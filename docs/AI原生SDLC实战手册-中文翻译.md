## 代码已经不再是瓶颈

企业已经开始用 AI 以一年前难以想象的速度编写代码，但围绕代码的流程并没有同步提速。

许多工程团队仍保留原来的审批关卡、代码审查、工作交接和政策要求。这些环节拖慢了 Claude Code 等智能体编程工具带来的生产力提升。

软件开发生命周期（Software Development Lifecycle，SDLC）是让软件从想法走向生产环境的一整套流程。大多数组织都采用某种形式的六阶段流程：规划、设计、构建、测试、部署和维护。传统上，每个阶段相互独立，并由不同角色负责：产品经理写需求，技术架构师把需求变成设计，工程师实现设计，受监管企业的 QA 团队负责验证，发布团队负责上线，运维团队监控运行状态。工作依靠文档、工单和签字审批在各阶段之间流转。

传统 SDLC 流程较重，是为了确保每一步都有人负责、受到控制。但它诞生于一个“写代码和实现功能最耗时、成本最高”的时代。如今，这个前提已经不再成立。PRD、估算仪式和产品安全评审，本来是为了让团队在持续数周、数月甚至数个季度的开发过程中保持一致。

传统 SDLC 的控制措施还默认每一步都由人来完成。真正从 AI 中获得最大价值的组织，已经围绕智能体 AI 的新能力重建流程，同时确保人类仍在关键环节参与决策。本指南结合 Anthropic Applied AI 团队为客户工作的经验，介绍如何在 SDLC 的每个阶段整合 Claude，以加快开发与流程流转。

当代码不再是瓶颈，构建阶段的速度快到传统 SDLC 跟不上时，会出现三件事：

- 瓶颈转移到构建阶段的前后环节，主要是规划、审查/测试和部署，因为这些环节仍以人的速度运行。
- 原有控制措施与现实脱节，甚至变得无法执行。代码由人编写时，逐行人工审查很合理；当大部分差异由智能体生成时，这种方式就跟不上了。
- 治理成本上升，因为各种例外仍要交给每周或每月才开一次的会议和委员会处理。

![构建已经不再是限制，周边仍以人的速度运行](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8739a1b934ffe55bfc9715_44592f18.png)

*构建已经不再是限制；真正限制速度的是周围仍由人推动的步骤。构建时间缩短到数小时，其他阶段的耗时却没有变化。*

以安全审查为例：安全团队的规模通常是按人工开发的产出来配置的。智能体让代码产出成倍增加后，要么审查队列越积越长，要么代码在审查不足的情况下上线。受监管组织无法接受任何一种结果，因此安全检查和政策检查也必须跟上智能体的速度。

要真正获得智能体 AI 的生产力收益，同时安全地使用它，传统 SDLC 必须经历与代码实现阶段同等程度的改造。

## 什么是 AI 原生 SDLC？

AI 原生 SDLC 是对开发流程的重新设计：保留传统流程的控制目标，但采用新的执行方式。流程不再是单向直线，而是一个持续循环；AI 被嵌入每一个环节。它通过自动交接并触发下一项工作，解决传统 SDLC 各阶段之间依赖人工、笨重低效的交接问题。

这种模式也常被称为“智能体 SDLC”“AI SDLC”或“智能体软件开发”。名称不同，指的是同一件事。

![AI 原生 SDLC 循环](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8858c2eccce183e7553cf2_53b010df.png)

### AI 原生 SDLC 六个阶段的变化

下表展示了传统 SDLC 与 Claude 支持的 AI 原生 SDLC 两个端点。现实中，大多数组织处在二者之间。


| 阶段       | 传统 SDLC                      | AI 原生 SDLC                                             |
| -------- | ---------------------------- | ------------------------------------------------------ |
| Plan     | 委员会收集需求，经过研讨会和层层签字，再由人手工写成文档 | Claude 直接从原始来源汇总痛点，写入人能读、机器也能执行的 `intent.md`           |
| Design   | 分析师写规格，设计师再理解并转化             | 在一次与智能体的工作会话中完成需求和设计；用 Skill 编码的标准约束过程，并在 Git 中做版本管理   |
| Build    | 测试和代码都由人手写，文档通常在主要开发完成后补写    | 测试和代码由 AI 生成；组织知识以机器可读、版本化的 `CLAUDE.md` 和 Skill 维护     |
| Test     | 在阶段边界设置 QA 关卡                | 把持续评测（eval）嵌入整个实现过程                                    |
| Deploy   | 人工逐行审查代码；治理依赖周期性的评审，执行往往不一致  | 使用多层智能体审查，仅把受监管和关键代码留给人审；通过 Hook 作为审批关卡，在 AI 行动时即时执行治理 |
| Maintain | 人工盯着生产环境找问题                  | 智能体监控线上部署；一旦指标越过控制带，就诊断问题，并把新的 `intent.md` 写回循环        |


右栏贯穿始终的是“已提交的产物”。每个阶段结束时，都把一项产物写入版本控制；下一阶段从读取它开始。这些产物包括 `intent.md`、`spec.md`、`plan.md`、代码差异及测试、包含审查结论的 PR，以及事故记录。

早期阶段主要使用 `.md` 文件，因为产品负责人和智能体都能读取并据此行动。从“构建”阶段开始，产物则变成代码及其记录。这条提交链本身也是审计轨迹：谁提出了什么、智能体产出了什么、谁批准了它。

凡是需要判断的决策，人类仍然承担最终责任。在智能体 SDLC 中，人的注意力会随着待审查产物的变化而转移。

> 每个阶段都要提交一份下一阶段可读取的产物。意图、规格、计划、代码差异和审查结论共同构成完整的审计轨迹。



## 实战方案（Plays）

“实战方案”是本手册的核心。它们分布在六个非线性阶段中：规划、设计、构建、测试、部署和维护；合在一起覆盖完整生命周期。

每项方案都会说明：

- 变化是什么；
- 如何起步；
- 具体实施步骤；
- 治理注意事项；
- 如何衡量是否有效。

这些方案是模块化的。组织可以根据自身需要，在不同时间优先改造不同阶段。每项方案都在“前置条件”中列出依赖关系，依赖图也会进一步说明。

一个阶段以提交产物结束，而这次提交会启动下一阶段：被接受的 `intent.md` 触发需求与设计；获批的 `spec.md` 触发计划模式；合并的 PR 触发流水线；生产环境中被突破的控制带则产生新的 `intent.md`，循环由此继续。

开始时，可以由人手动提示并启动每一步。最终目标是形成一个闭环：每项被接受的产物都会自动触发下一道关卡。人的注意力集中在关卡上，审查智能体标记的问题，而不是每次都从零启动一个阶段。

![实战方案的采用顺序与依赖关系](https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a8855c75344623fc81efcb8_5d5a3c05.png)

*图中的方案按所属阶段排列，箭头表示建议采用顺序；二者并不相同。可以从任何陶土色方案开始，因为没有箭头指向它，说明它不依赖其他方案。对于其他方案，应先采用所有箭头指向它的前置方案。*

## 阶段 1：规划

> 想法不再等待某个人把它写成正式文档。提出者只需用自己的话记录一次意图，并把它保存成有版本控制、可供下一阶段直接使用的产物。



### 把想法记录为 `intent.md`

启动软件开发流程的 `intent.md` 可以来自不同入口：某个人提出一个想法、有人创建一张工单，或者监控告警暴露了一起事故（参见“阶段 6：维护”）。

当一个人产生想法时，他可以和 Claude 一起头脑风暴，生成 Markdown 格式的初步规格。在传统 SDLC 中，这个人还必须说服产品团队成员，让对方与自己一起或代替自己把想法写成正式文档。

Claude 生成的初步规格既方便人阅读，又有版本控制，下一阶段也能立即使用。它被保存为 `intent.md`。

无论意图来自事件触发还是智能体，后续步骤都相同：产品负责人审查并修正智能体编写的 `intent.md`，然后再提交。


| 传统方式                                                                               | AI 原生方式                                                                                       |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 一个想法要先后经过待办事项、用户故事、故事点和需求梳理会议，之后才有人能够行动。每次交接都会转移所有权，因此工程团队最终收到的内容，往往已经偏离提出者的原意好几层。 | 提出者与 Claude 头脑风暴，并把结果写成 `intent.md`。这是一份用提出者自己的语言编写的初步规格，包含“想要什么、为什么需要、有哪些约束”。重复流程则编码成 Skill。 |




#### 如何起步

**前置条件：** 无。

**基础设施：**

- 为非工程人员提供 Claude 使用权限（claude.ai 或 Cowork）；
- 约定统一的 `intent.md` 模板；
- 准备一个共享、有版本控制、由产品负责人关注的“意图存放处”。

对于单一产品，最简单的做法是在产品仓库中建立 `intent/` 目录，让产物链与由它生成的代码放在一起。只有当意图横跨多个仓库时，单独建立意图仓库才值得额外成本；在单体仓库（monorepo）中，用一个目录即可。阶段 3 的侧栏还会说明这个存放处如何与已经作为正式记录的 Jira 或需求工具协作。

搭建工作只需由平台或工程团队完成一次。技术团队成员需要创建意图存放处，并决定谁有写入权限，因为贡献者可能来自组织的许多部门。

仓库建好后，不熟悉 Git 的贡献者无需直接操作 Git。可以通过版本控制系统连接器（如 GitHub），让 Claude 在 claude.ai 或 Cowork 中代其提交 Markdown 文件。

#### 执行步骤

1. 提出者用自己的话向 Claude 描述问题：当前做不到什么、哪些人受影响、理想状态是什么、哪些内容不在范围内等。无需正式术语。
2. 与 Claude 继续讨论，直到想法足够具体。Claude 会像分析师一样追问范围、用户、约束和成功标准。
3. 要求 Claude 使用组织模板写成 `intent.md`。模板可以由技术人员制作成 Skill，再由负责人批准，其中可包含问题、预期结果、受影响的用户和系统、约束条件及待确认问题。
4. 提出者修正 Claude 的误解。
5. 把 `intent.md` 提交到共享位置。作者和时间戳会进入记录，产品负责人随后从这里接手。



#### 示例：`intent.md`

```markdown
# 意图：让客户自助查询理赔状态

作者：J. Ortiz（理赔运营）  状态：草稿

## 问题

客户需要打电话给联络中心，询问理赔处理到哪一步。
理赔处理人员约三分之一的通话时间都花在单纯查询状态上。

## 预期结果

客户可以在门户中看到理赔状态、下一步操作和预计日期。

## 受影响的用户和系统

理赔处理人员、门户团队、claims-core API。

## 约束

门户会话中不得新增个人身份信息（PII），只使用现有身份认证。

## 待确认问题

第三方损失理算员是否也需要访问？
```



#### 治理注意事项

治理证据就是已提交的 `intent.md`。其中记录作者、时间戳和完整修订历史，并保存在意图存放处的 Git 历史中。产品负责人负责批准；把意图送入阶段 2（设计）的接受或拒绝决定，以合并记录或关闭审查的形式保存。

#### 如何衡量

- **领先指标：** 从第一次讨论到提交 `intent.md` 所需的时间，可从包含作者和时间戳的 Git 历史中读取。目标是把原本持续数周的需求挖掘与梳理缩短到数小时。
- **滞后指标：** “存活率”，即有多少 `intent.md` 被产品负责人接受并进入阶段 2，而不是被关闭。接受/拒绝分别记录为产物合并或审查关闭。还应统计同一变更的首个 `spec.md` 提交后，`intent.md` 又被修改了多少次。



## 阶段 2：设计

> 把需求与设计压缩到一次会话中完成。政策在规格编写时就得到应用，不必等到数周后的评审才发现问题。



### 需求与设计

产品负责人批准 `intent.md` 后，Claude 会据此生成需求和设计规格。组织针对品牌、安全、合规及用户体验编写的 Skill 会指导这一过程。

产品负责人只负责审查规格，而不必亲自编写。目标是形成一份工程团队可以据此规划的 `spec.md`，并明确标出需要关注的问题。

前端开发是最直观的例子：`intent.md` 获批后，产品负责人可在 Claude Design（测试版）中根据它生成设计原型，不断迭代，再导出到 Claude Code 进行构建。


| 传统方式                                                                 | AI 原生方式                                                              |
| -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 需求与设计是由不同团队负责的独立阶段。分析师先把想法正式化为需求，设计师再把需求理解并转化为设计。这样做便于追责，却缓慢且容易丢失信息。 | 两个阶段在一次提示会话中完成。Claude 读取 `intent.md`，在组织 Skill 的约束下生成需求和设计规格，并标出风险点。 |




#### 如何起步

- **前置条件：** 已有 `intent.md`；品牌、安全、合规和 UX 政策已经写成 Skill。
- **基础设施：** 一名拥有 Claude 使用权限的产品负责人，不要求具备工程技能。



#### 执行步骤

1. 产品负责人打开一个能使用组织 Skill 的会话，并附上 `intent.md`。
2. 在提示中明确引用 `intent.md`、列出约束，并要求标记风险。开始时手动执行；成熟后，把它固化成组织级斜杠命令。再进一步，可让意图存放处合并 `intent.md` 的事件自动触发非交互式任务：加载组织 Skill、生成 `spec.md`，并以 PR 形式提交。这样产品负责人的首次介入就是审查。（自动化管道参见阶段 5。）
3. 由同一位产品负责人对照原始想法审查规格：它是否解决了所述问题？`intent.md` 中的待确认问题是否得到回答或明确保留？
4. 优先处理被标记的风险点，因为这些正是分析师原本会升级处理的问题。产品负责人应在工程团队看到规格前，与相应政策负责人逐项解决。
5. 把 `spec.md` 与 `intent.md` 放在一起提交。这一对文件记录“提出了什么”和“最终决定了什么”。
6. 产品负责人决定是否把规格和意图推进到构建阶段。对于组织定义的高风险事项，应咨询技术负责人。这个决定必须由人作出；接受规格会启动阶段 3 的计划模式。



#### 提示词示例

```text
阅读随附的 intent.md，并为把它集成到现有代码库中生成一份需求与设计规格。
应用你可以使用的 Skill，确保方案符合我们的品牌指南、安全政策和 UX 标准。
把完整规格写入 spec.md，使其可以直接交给工程团队。
清楚说明所有风险点，尤其是你无法同时满足相互冲突政策的地方。
```



#### 治理注意事项

正在生效的政策会在规格编写时被读取和应用，而不是数周后才在评审中发现。组织 Skill 作为规格的约束。规格、生成它的提示词，以及当时生效的 Skill 版本都会记录在版本控制中。产品负责人签字批准规格，并把已标记问题交给对应的政策负责人。

#### 如何衡量

- **领先指标：** 同一变更从提交 `intent.md` 到提交 `spec.md` 的耗时（两个 Git 时间戳），并与过去“需求 + 设计”的周期比较。
- **滞后指标：** 构建开始后的需求返工量。统计同一变更在首次提交 `plan.md` 后又发生了多少次 `spec.md` 提交，Git 日志可直接给出数据。



## 阶段 3：构建

> 没有被接受的计划，就不开始实现。组织知识成为智能体会读取的文件，护栏则以代码运行，而不再只是人的习惯。



### 默认从 Claude Code 计划模式开始

工程师以计划模式启动 Claude Code，提供阶段 2 已批准的 `spec.md`。Claude 会向工程师提问，双方反复完善方案，直到工程师认可。


| 传统方式                                                                               | AI 原生方式                                                                     |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 工程师读完设计便开始写代码。具体改哪些文件、做哪些测试，通常只存在其脑中，最多写在工单评论里，别人无法提前审查。审查者第一次看到的是完整代码差异，此时返工已经很慢。 | Claude 在只能读取、不能修改代码库的计划模式中先写出明确计划。工程师在代码产生前纠正它，再把批准版本提交为 `plan.md`，供后续阶段核对。 |




#### 如何起步

- **前置条件：** 如果存在，应提供意图产物（`intent.md` 或 `spec.md`）；有 `CLAUDE.md` 会更好。
- **基础设施：** Claude Code 及其对代码仓库的访问权限。



#### 执行步骤

1. 工程师在计划模式中启动 Claude 会话。
2. 提供 `intent.md` 和 `spec.md`，要求实现计划明确要修改的文件、工作顺序和用于证明正确性的测试。
3. 质询计划：这项改动可能破坏什么？哪一步风险最高？Claude 还考虑过哪些未采用的方案？
4. 持续迭代，直到一个从未看过此前对话的工程师，仅凭计划就能完成实现。
5. 把批准的计划提交为 `plan.md`。它会进入审计轨迹；阶段 5 的 PR 审查会核对最终差异是否与计划一致。
6. 接受计划并让 Claude 实现。有了可靠计划，实现往往一次即可完成。
7. 如果实现偏离计划，应在同一提交中更新 `plan.md`；可以考虑用 Hook 强制两者保持同步。



#### 示例：`plan.md`

```markdown
# 计划：让客户自助查询理赔状态（来自 intent.md，2026-06-02）

## 要修改的文件

- portal/src/claims/StatusPanel.tsx（新增）
- claims-api/routes/status.py
- claims-api/tests/test_status.py

## 工作顺序

1. 在现有身份认证之后添加状态接口。
2. 创建调用该接口的面板。
3. 把面板接入门户导航。

## 风险

claims-core API 的限流为 50 rps，因此面板必须使用缓存。

## 验证方式

test_status.py 覆盖四种理赔状态；截图与批准的设计稿一致。
```



#### 治理注意事项

设计审查发生在生成任何代码之前，此时改变方向只需修改文档。计划模式本身会执行这一约束：工程师接受计划前，Claude 不能编辑文件。计划及其修订、批准人都会被记录。日常改动可由工程师批准；组织定义的高风险事项则交给技术负责人或架构师。

#### 如何衡量

- **领先指标：** 首次实现就成功合并的变更占比，以及从计划批准到 PR 合并的时间；所需数据写入 PR 元数据。
- **滞后指标：** 每项变更的返工轮次，以及合并后的代码差异与已提交 `plan.md` 的一致频率。



### Claude Code 自动模式

Claude Code 还可以在自动模式下运行：工程师反复完善并批准计划后，Claude 无需每次编辑都请求确认即可应用改动。随着后续方案的护栏成熟——例如调优后的 `CLAUDE.md`、编码政策的 Skill、阻止不安全行为的 Hook，以及 Claude 能自行运行的测试套件——自动接受会成为日常工作的默认选择。适合这种模式的任务应有严谨的 `spec.md`、较小的影响范围，并且现有测试已覆盖相关代码。

关注点会从“盯着智能体每次编辑、逐个审查动作”，转向“在更长的自主会话结束后审查产物”。配合 Git worktree 使用时，自动接受还能让个人和团队并行开展更多工作，也是阶段 6 中自主运行 SDLC、闭合循环的基础。

> **侧栏：遗留系统与唯一事实来源**
>
> 这一原则适用于流程产生的所有产物。现有 SDLC 往往已经在跟踪它们，只是不使用 Markdown：工作项可能在 Jira，带监管追踪能力的需求工具中保存需求，Figma 中保存设计，变更委员会管理审批。这些系统很难替换，因为审计方和监管方已经接受它们，其他团队也依赖它们。因此，AI 原生 SDLC 必须与现状配合。
>
> 对每类产物，应指定一个系统作为唯一事实来源，其他位置只保存副本或原始记录链接。可按产物选择以下配置：
>
> - **以代码仓库为准：** Markdown 产物是权威记录，遗留系统引用具体提交中的文件。对工程主导的组织而言，这很清晰，因为全部记录共用一个工具和一套时间戳。
> - **以遗留系统为准：** Jira、ServiceNow 或需求工具保存权威记录，Markdown 只是工作副本。Claude 在会话开始时读取记录，并在生成规格或计划的同一会话中通过 MCP 连接器把结果写回。
> - **最低要求是双向关联：** 每份产物都注明记录 ID，每条遗留系统记录都包含 Markdown 文件的提交 SHA。迁移早期可以先这样做，即便暂时存在两个事实来源。
>
> 两套系统可以共存，但必须相互链接，或者明确声明其中一个才是事实来源。



### `CLAUDE.md`

`CLAUDE.md` 为 Claude 提供新成员入职时需要的上下文，包括团队约定、命令、架构，以及团队最常遇到的错误。原本藏在人脑和 Wiki 中的知识，变成智能体每次会话开始都会读取的文件；整个团队共同维护它，每次出现错误时继续完善。

#### 如何起步

- **前置条件：** 无。
- **基础设施：** 一个代码仓库、已安装 Claude Code，以及一名熟悉代码库的工程师。



#### 执行步骤

1. 在仓库中运行 `/init`，Claude 会根据发现的内容生成初始 `CLAUDE.md`。
2. 精简文件，只保留新成员第一天真正需要的内容：构建、测试和 lint 命令；重要约定；Claude 经常犯错的地方。
3. 把根目录中的 `CLAUDE.md` 提交到 Git，让团队共享同一版本，并像审查代码一样审查它的变更。
4. 可以采用一条简单规则：Claude 同一个错误犯两次，就把纠正方法写入 `CLAUDE.md`。
5. 最好控制在一页以内。Claude 每次会话开始都会读取全文，过时内容只会浪费上下文。



#### 示例：`CLAUDE.md`

```markdown
# 支付服务

## 命令

- 构建：make build
- 测试：make test（单元测试）、make itest（集成测试，需要 Docker）
- Lint：make lint（CI 中会运行；推送前先修复）

## 约定

- Java 21、Spring Boot 3，不再新增 Lombok。
- 金额始终使用 BigDecimal，绝不使用 double。
- 每个端点都必须在 src/itest 中有集成测试。

## 架构

- api/ 放 REST 控制器，core/ 放领域逻辑，adapters/ 与外部系统通信。
- Kafka 事件定义在 schemas/ 中；绝不编辑生成的类。

## Claude 容易犯的错误

- 不要升级依赖版本；它们由平台团队负责。
- 遗留的 v1/ 包已经冻结；改动应放入 v2/。
```



#### 治理注意事项

`CLAUDE.md` 受版本控制，因此智能体遵循的指令可审查、可审计。团队约定通过该文件统一应用，所有改动都记录在 Git 历史中，并由代码所有者在 PR 审查中批准。

#### 如何衡量

- **领先指标：** Claude 重复犯下本应由 `CLAUDE.md` 防止的错误的次数；对文件的纠正和修改可从 Git 历史跟踪。
- **滞后指标：** 新团队成员从加入到合并第一个 PR 的时间，可从 PR 历史获得。



### 用 Skill 承载组织知识

Skill 能把组织知识真正投入运行：指令明确、受版本控制、广泛应用，并在政策变化时集中更新。经验法则是：需要稳定一致地应用的组织知识，应写成 Skill；属于单个仓库工作上下文的内容放进 `CLAUDE.md`，一次性要求则放在提示词中。

#### 如何起步

- **前置条件：** 无。已有 `CLAUDE.md` 会有帮助，但 Skill 不依赖它。
- **基础设施：** 一项有明确负责人和书面权威来源的政策。



#### 执行步骤

1. 选择一项目前执行不一致的知识，例如安全标准、API 设计约定或品牌规则。
2. 把它写成 Skill：创建包含 `SKILL.md` 的目录，在 frontmatter 中说明何时触发，在正文中说明要做什么。工程师可在 Claude 协助下，根据政策负责人的权威文件编写。
3. 把 Skill 放在仓库的 `.claude/skills/<name>/` 中，使其随代码发布；也可以通过插件在组织范围内分发。
4. 测试 Skill 能否正确触发：用不同说法要求 Claude 完成相关任务，确认它每次都会加载。
5. 政策变化时同步修改 Skill，并由政策负责人批准。
6. 工程师会在下次会话中自动使用新版本。



#### 示例：`.claude/skills/secure-api-review/SKILL.md`

```markdown
---
name: secure-api-review
description: 应用 API 安全标准。在创建或修改面向外部的端点、
  审查 API 代码或生成 OpenAPI 规格时使用。
---

# 安全 API 审查

创建或修改 API 端点时：

1. 身份认证：每个端点都必须使用网关 JWT；除 /health 外不得匿名访问。
2. 输入验证：根据 OpenAPI schema 验证请求体，并拒绝未知字段。
3. 审计：每个改变状态的端点都要发出审计事件，包含操作者、动作、实体和时间戳。
4. 数据分类：schema 中标记为 pii 的字段绝不能出现在日志或错误消息中。

运行 scripts/check-endpoints.sh，并在总结中附上输出。
```



#### 治理注意事项

Skill 是一种控制，但属于建议性控制。它会让 Claude 在编写代码时更可能应用政策，却不能强迫每个会话都遵守。必须无条件成立的政策，需要在 Skill 背后增加确定性措施，例如阻止操作的 Hook，或在 PR 阶段重新核对政策的审查。Skill 让违规变得少见，Hook 则让违规几乎不可能发生。Skill 的调用会记录在会话轨迹中，政策负责人应像审查代码一样审查 Skill 变更。

#### 如何衡量

- **领先指标：** 从政策负责人批准变更到新版 Skill 合并的时间，可从 Skill 目录对应的 PR 获取。
- **滞后指标：** PR 审查中引用该政策的问题数。Skill 在编码阶段正确执行后，这一数字应趋近于零；如果没有下降，说明 Skill 没有触发，或其内容已偏离正式政策。



### 用 Hook 建立构建期护栏

Skill 是建议性控制，Hook 则是它背后的确定性控制层。Claude 在实现阶段的大多数动作都是编辑文件和执行 shell 命令，因此 Hook 往往在构建阶段触发最频繁。

构建期 Hook 可以：

- 阻止编辑生成类、冻结软件包等受保护路径；
- 每次编辑后运行格式化器和 linter，避免偏差积累；
- 防止凭证进入代码差异。

凡是必须无例外执行的政策，都应为相应 Skill 配置确定性控制。Hook 会对每个匹配动作运行，因此构建期 Hook 应快速，并只检查发生变化的文件。完整测试套件等较重检查应放到提交或 PR 阶段。

需要人批准的 Hook 则应归入阶段 5 的审批关卡。如果构建时不断要求人工批准，就会让人重新回到所有并行会话的关键路径上。

### 并行会话与子智能体

一名工程师可以同时推动多条工作流。

“并行会话”是另一个完整的 Claude Code 实例，在自己的 Git worktree 中处理独立任务。各会话彼此一无所知，唯一共享的是负责引导它们的工程师。

“子智能体”在单个会话内部运行，是有独立上下文窗口和工具限制、职责明确的助手，适合多个任务中反复出现的工作，例如验证应用是否按预期运行。

并行会话增加一名工程师可以同时推进的任务数；子智能体让每个会话专注于自己的任务。工程师的工作变成引导和审查它们。


| 传统方式                                                                   | AI 原生方式                                                                                       |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 一名工程师一次处理一个任务，每天或每周大量时间耗在构建、测试和等待审查上。等待时虽然可以切换任务，但上下文切换很累，很少有人愿意频繁这样做。 | 一名工程师同时运行多个 Claude 会话，每个会话在独立 worktree 中处理独立任务。重复工作变成拥有独立上下文和工具限制的子智能体。工程师逐渐转向编排，最终负责构建和监控闭环。 |




#### 如何起步

- **前置条件：** 所有会话都会读取的 `CLAUDE.md`。阶段 4 的反馈闭环也很重要，因为能自行验证工作的会话较少需要工程师监督。
- **基础设施：** Git 仓库；用 worktree 隔离会话；调好权限设置，避免组织认定安全的命令仍不停等待批准。



#### 执行步骤

1. 根据计划模式生成的方案，把工作拆成修改不同文件的独立任务。会改到同一文件的任务应放在一个会话中依次执行。
2. 每项并行任务使用自己的 worktree，例如一个终端运行 `claude --worktree feature-auth`，另一个运行 `claude --worktree fix-rate-limit`。独立检出和分支可以防止会话在文件上相互冲突。
3. 从两到三个会话起步。实际并发上限取决于一个人能认真审查多少条工作流；只有在审查跟得上时才继续增加。
4. 把重复工作做成子智能体，在 `.claude/agents/` 的 Markdown 文件中定义名称、使用时机和可用工具。例如：主智能体完成后删除多余复杂度的代码简化器；运行应用并检查行为的验证器；只探索代码库并汇报、不挤占主上下文的研究员。把定义提交到 Git 供全团队共享。



#### 示例：`.claude/agents/verifier.md`

```markdown
---
name: verifier
description: 在会话报告完成前运行应用并检查改动是否有效
tools: Bash, Read
---

使用 make run 启动应用。操作已修改的功能，以及与它最近的两条相邻流程。
报告你运行了什么、观察到了什么，以及任何与 plan.md 不一致的行为。
不要修复，只做报告。
```



#### 治理注意事项

会话越多，产出越多，因此控制必须来自仓库中的统一配置。Hook 和权限设置会应用到全部会话；每个会话的操作都会被记录，并归因到运行它的工程师。

#### 如何衡量

- **领先指标：** 在审查质量不下降时，每名工程师的并发会话数（可从 OpenTelemetry 导出统计），以及一天中用于引导而非等待的时间占比。
- **滞后指标：** 每名工程师每周合并的变更数，同时结合 PR 历史计算的返工率观察。



## 阶段 4：测试

> 每个会话都要在交给人查看之前检查自己的工作；用于引导智能体的配置，也要像智能体编写的代码一样接受回归测试。



### 给 Claude 一个反馈闭环

始终为 Claude 提供验证自身工作的方法，例如运行测试、执行构建或比较截图。会话先自行检查并修正错误，再把结果交给工程师。

反馈闭环不要与阶段 3 的验证子智能体混淆。反馈闭环贯穿整个任务，工作迭代多少次，它就运行多少次；验证子智能体则是一种最终检查的封装方式——主会话认为完成后，另开一个全新上下文来验证，避免结论受到生成代码时那些假设的影响。


| 传统方式                                                                              | AI 原生方式                                                                     |
| --------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 代码是否可用的信号来得很晚：几分钟后来自 CI、几天后来自测试人员、几周后来自生产环境。智能体生成代码后，延迟反馈意味着人必须检查它的全部产出，这个人就成了瓶颈。 | 在人查看前，让会话自行运行测试、构建或截图检查。Claude 反复修正直至通过，因此工程师收到的结果已经完成机械验证。反馈闭环由运行会话的工程师搭建。 |




#### 如何起步

- **前置条件：** 无。
- **基础设施：** 能分别通过一条本地命令运行的测试套件和构建流程。对于 UI 工作，必须让 Claude 能看到结果，可使用浏览器工具，或通过 MCP 接入截图工具。



#### 执行步骤

1. 如果目前验证工作需要一串命令和环境知识，就把它封装为 `make test`、`npm test` 等单一目标；失败时必须返回非零退出码。
2. 在 `CLAUDE.md` 的“命令”部分列出每条命令，并给出成功输出的示例。
3. 设置可量化目标，让 Claude 无需询问即可判断，例如：“`test_status.py` 中所有测试通过”“截图与随附设计稿一致”或“端点返回 200 且包含新字段”。
4. 修复缺陷时先写失败测试。让 Claude 用测试复现缺陷，运行并确认它按预期原因失败，然后先提交测试。之后才要求 Claude 在不编辑测试的情况下让它通过，并用测试文件 Hook 强制执行。修复前就存在且智能体无法改写的测试，才是缺陷已消失的可靠证据。
5. UI 工作使用视觉反馈闭环：提供浏览器或截图工具和设计稿，让 Claude 按“实现 → 截图 → 比较 → 调整”的顺序迭代。两三轮很正常，每轮都应更接近目标。
6. 把验证写进“完成”的定义，并将指令保存在 `CLAUDE.md`：报告完成前必须运行测试并展示输出。
7. 保护反馈闭环本身。修代码的智能体不能削弱检查代码的测试。可以用 Hook 阻止修复任务编辑测试文件；或者在审查差异时拒绝任何修改测试的变更。



#### `CLAUDE.md` 中的验证块示例

```markdown
## 验证你的工作

- 构建：make build（必须以“Build succeeded”结束）
- 测试：make test（全部通过；绝不跳过或删除失败测试）
- Lint：make lint（零警告）

报告任何任务完成前都要运行以上三项，并粘贴输出。
测试失败时，修代码，不要改测试。
```



#### 治理注意事项

- **强制执行什么：** 任务报告完成前必须验证；修复期间禁止智能体编辑测试文件。如果组织要求保证执行，就把两者做成 Hook。
- **证据是什么：** Claude 实际运行并粘贴的 `make test` 输出、构建日志或截图差异，证据直接来自工具链。
- **记录在哪里：** 会话记录会由 OpenTelemetry 导出到组织的可观测性系统；PR 的检查运行中也会保存，审查者和未来的审计人员都能查看。
- **谁批准：** 审查 PR 的代码所有者。机械验证已经附上，因此其注意力可以集中在意图和风险上。



#### 如何衡量

- **领先指标：** 智能体编写的变更首次通过 CI 的比例，现有 CI 系统通常已经能统计。
- **滞后指标：** 每个 PR 的审查时间；测试接替审查者发现机械问题后，该指标应下降。还应观察事故跟踪系统中的变更失败率。



### 在 CI 中持续运行评测

评测（eval）相当于 AI 原生时代的阶段式 QA 关卡。实践中，它是一套在智能体配置变化时运行的测试。当替换新模型或改写提示词后，评测套件能判断智能体是否仍以相同标准完成工作。

评测应被视为持续维护的“活”套件。模型改进后，过去能区分优劣的案例可能不再有意义；同时要把持续监控发现的新问题加入套件。

有些团队会根据用例，选择按固定周期离线运行，而不是每次变更都运行。以下步骤针对持续评测。

#### 如何起步

- **前置条件：** `CLAUDE.md` 和本阶段的反馈闭环。
- **基础设施：** 能以非交互方式运行 Claude Code 的 CI，以及有足够评测预算的 API 密钥。



#### 执行步骤

1. 平台工程师从近期真实工作中收集 20～50 个任务，并保留每个任务预期或已接受的结果。
2. 把每项任务写成评测：包括提示词，以及定义“可接受”的检查条件（测试通过、lint 干净、行为未改变、遵守政策等）。
3. 在 CI 中按计划非交互运行；只要 `CLAUDE.md`、Skill 或 Hook 有变化也要运行，因为这些配置会引导智能体，理应像代码一样接受回归测试。
4. 根据评测结果决定配置能否合并。若某次 Skill 修改导致通过率下降，应先审查再合并。
5. 每起生产事故都由负责团队写成一项评测，并永久留在套件中作为回归测试。



#### 示例：`.github/workflows/agent-evals.yml`

```yaml
name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
```



#### 治理注意事项

评测为 QA 提供了一道能跟上智能体产出速度的关卡。通过率阈值作为合并检查强制执行；每次运行都留有记录，可比较长期变化；拥有相应配置的团队负责批准变更。

#### 如何衡量

- **领先指标：** 每次运行报告的评测通过率趋势；以及生产事故转化为永久评测所需的时间。
- **滞后指标：** CI 捕获的回归问题与生产环境才发现的回归问题之比，可从事故跟踪系统计算。



## 阶段 5：部署

> 审查是双向的，治理在智能体行动时即时执行。智能体可以完成生产关卡之前的一切，但绝不能越过关卡。



### 把 AI 放进 PR 审查闭环

Claude 既发起审查，也接受审查：它按照组织政策审查收到的 PR，并自行处理自己 PR 上的审查意见。这样，工程师可以把 PR 审查精力放在行为层面，即判断变更意图和风险。


| 传统方式                                                     | AI 原生方式                                                         |
| -------------------------------------------------------- | --------------------------------------------------------------- |
| 审查能力按人工产出来规划。PR 等待审查者读完全部内容；审查质量随审查者负载变化；作者不断催促，积压却继续增长。 | 每个 PR 都经过同样的一组审查轮次，问题按严重程度排序。人的注意力上移到两个问题：变更是否实现了计划意图，风险是否可以接受。 |




#### 如何起步

- **前置条件：** 阶段 3 更新后的 `CLAUDE.md`；若审查要执行书面政策，还需相应 Skill 和已定义的子智能体。
- **基础设施：** 安装 Claude 集成的代码仓库。可由管理员启用托管 Code Review（研究预览），也可在自有 CI 中运行 `claude-code-action`；需要时通过 AWS Bedrock、Google Vertex 或 Microsoft Foundry 调用模型。最好同时启用必须由代码所有者批准的分支保护。



#### 执行步骤

1. 最快的起点是托管 Code Review：管理员启用并选择仓库。若需要自行控制流水线，或让 API 调用走组织自己的云协议，则在 CI 中用 `claude-code-action` 运行审查。
2. 技术负责人在仓库根目录编写 `REVIEW.md`，把政策分成组织关心的多轮审查：缺陷和逻辑错误；安全与漏洞；相对于 `spec.md`、`plan.md` 和设计原则的合规性。还要定义什么是“重要问题”、什么只是“小建议”，以及哪些内容无需报告。
3. 技术负责人设置人工审批门槛。AI 的发现本身不能批准或阻止 PR，分支保护仍要求代码所有者批准。若平台工程师确实希望根据发现阻止合并，可以读取检查任务发布的机器可读严重性计数。
4. 审查者或作者在评论中标记 `@claude` 后，Claude 会处理意见并推送修复；PR 线程同时记录请求和变更。此修复闭环通过 `claude-code-action` 运行。在托管服务中，评论 `@claude review` 则会请求重新审查。对于 Claude 自己创建的 PR，还可以让它持续跟进直到可合并：团队用自定义斜杠命令循环扫描未解决评论和失败检查，修复并推送，直至 PR 变绿，只等代码所有者批准。
5. 审查发现要反馈到 `CLAUDE.md`。同类错误第二次被指出时，就在此次审查中把纠正方法写入文件。由于后续审查会读取 `CLAUDE.md`，从下一个 PR 开始便能捕获该错误。审查也应指出代码变更是否让 `CLAUDE.md` 过时。
6. 技术负责人每月调优：评价审查发现以改进审查器，并在 `REVIEW.md` 中限制小建议数量。排除生成路径和 CI 已经强制检查的内容。



#### 示例：`REVIEW.md`

```markdown
# 审查说明

## 审查轮次

执行三轮，并标明每个发现来自哪一轮：

- 缺陷：逻辑错误、损坏的边界情况、隐蔽回归
- 安全：注入风险、身份认证缺口、日志中的 PII
- 合规：变更符合 spec.md、plan.md 和我们的设计原则

## 什么才算“重要”

只有会破坏行为、泄露数据或违反政策的问题才标为“重要”。
风格和命名属于小建议。

## 限制小建议

每次审查最多报告五条小建议，其余只给出总数。

## 不要报告

src/gen/ 下的生成文件，以及 CI 已经强制检查的内容。
```



#### 治理注意事项

职责分离得以保留，因为编写代码的智能体无权批准代码。`REVIEW.md` 中的政策应用于所有 PR；发现、修复、评级和批准都记录在 PR 历史中，因此 PR 本身就是审计记录。最终由人通过分支保护批准，并参考 AI 的审查发现。

有关这些控制措施如何组合成生产级体系，可参阅 Anthropic 的[《如何保护 AI 原生软件开发生命周期》](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)。

#### 如何衡量

- **领先指标：** 首次审查所需时间，应降至分钟级；以及无需人接触分支就解决的审查意见占比，数据直接保存在 Git 中。
- **滞后指标：** 合并前捕获的缺陷和漏洞，相对于逃逸到生产环境的问题数量，可从 PR 历史和事故跟踪系统获取。



### 用 Hook 作为审批关卡

阶段 3 使用 Hook 作为无需人参与的护栏，允许或阻止动作。Hook 也可以“询问”：暂停动作，直到特定人员批准。这正是发布关卡所需要的能力。

本方案放在部署阶段，是因为发布关卡最直观；但 Hook 并不限于部署。它可在 Claude 行动的任何地方运行。例如阶段 3 中，没有变更工单时阻止修改迁移和基础设施；阶段 4 的修复任务中，阻止智能体编辑测试文件。

#### 如何起步

- **前置条件：** 无。
- **基础设施：** 一份书面清单，列出变更流程要求的全部审批。



#### 执行步骤

1. 工程管理层与变更管理、合规团队一起列出必须保留的人工审批关卡，如变更管理签字、发布授权、编辑受保护路径。
2. 平台工程师把每个关卡实现为 Hook：在 Claude 行动前运行的脚本，结果可以是允许、询问或阻止。
3. 团队 Hook 放入 Git 中的 `.claude/settings.json`；不可妥协的 Hook 放入由平台或 IT 管理员控制的托管设置，个人工程师无权关闭。
4. 阻止操作时要说明原因。Hook 的理由和获得批准的路径应出现在 Claude 的输出中。



#### 示例：`.claude/settings.json`

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/production-gate.sh"
          }
        ]
      }
    ]
  }
}
```

关卡脚本 `.claude/hooks/production-gate.sh`：

```bash
#!/bin/bash

# 生产部署必须有指定的发布授权
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "生产部署需要发布授权。" >&2
    exit 2 # 退出码 2 阻止动作；消息会返回给 Claude
  fi
fi
exit 0
```



#### 治理注意事项

Hook 就是审批关卡。关卡条件对所有人、每一次操作都执行。允许和阻止决定都带时间戳记录。关卡还定义“怎样才算批准”，例如已有获批的变更工单，或发布经理已经签字。

#### 完整示例：受监管企业的托管设置

以下配置由平台团队通过 MDM 或管理控制台部署，工程师不能编辑或覆盖：

```json
{
  "permissions": {
    "deny": [
      "Read(.env*)", "Read(./secrets/**)",
      "WebFetch", "Bash(curl *)", "Bash(wget *)"
    ],
    "allow": [
      "Bash(git *)", "Bash(make build)",
      "Bash(make test)", "Bash(make lint)"
    ],
    "disableBypassPermissionsMode": "disable"
  },
  "allowManagedPermissionRulesOnly": true,
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": ["git.internal.example.com", "registry.npmjs.org"]
    },
    "credentials": {
      "files": [
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" }
      ],
      "envVars": [{ "name": "GITHUB_TOKEN", "mode": "deny" }]
    }
  },
  "allowManagedHooksOnly": true,
  "disableSideloadFlags": true,
  "allowManagedMcpServersOnly": true,
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "example-corp/approved-plugins" }
  ],
  "requiredMinimumVersion": "2.1.193"
}
```

每项设置带来的控制效果：

- `permissions.deny` 防止秘密进入智能体上下文，并阻止工具任意访问网络；`permissions.allow` 预先批准安全的日常循环，避免拒绝清单造成频繁确认。
- `disableBypassPermissionsMode` 与 `allowManagedPermissionRulesOnly` 确保工程师、项目文件或命令行参数都不能放宽规则。
- `sandbox` 补上权限系统的缺口：工具层禁止 `WebFetch` 并不能阻止 shell 访问网络，而操作系统层的域名白名单能彻底限制外联。
- `failIfUnavailable` 与 `allowUnsandboxedCommands` 让沙箱成为真正关卡：沙箱无法初始化时 Claude Code 拒绝启动；沙箱内失败的命令不能转到沙箱外重试。
- `credentials` 补上拒绝规则的另一处缺口：文件工具虽受 `permissions.deny` 管理，沙箱中的 shell 默认仍可能读取 `~/.ssh` 或 `~/.aws/credentials`。该配置禁止这些读取，并从每条沙箱命令的环境中移除指定秘密。
- `allowManagedHooksOnly` 表示只能运行本方案定义的托管审批 Hook，本地配置不能新增或替换它们。
- `disableSideloadFlags` 与 `strictKnownMarketplaces` 确保工程师机器上的 Skill、智能体、Hook 和 MCP 服务器都来自组织批准的插件市场，而不是个人主目录。
- `allowManagedMcpServersOnly` 把智能体可用工具变成由平台团队控制的白名单。
- `requiredMinimumVersion` 拒绝低于批准版本的客户端，确保控制措施由组织真正评估过的构建版本执行。

这只是一份应按实际情况调整的起点，不建议原样复制。每条拒绝规则都会牺牲部分能力；正确平衡取决于仓库的数据分类。完整键说明见[设置参考](https://code.claude.com/docs/en/settings)。

#### 如何衡量 Hook

- **领先指标：** 每个审批关卡的等待时间。每次 Hook 决定都会以带时间戳的允许/阻止结果写入 OpenTelemetry 导出，因此可按关卡观察。
- **滞后指标：** 引入 Hook 前后，仍进入生产环境的关卡违规数量，可从事故跟踪系统统计。



### CI/CD 集成与部署

在 CI/CD 流水线中非交互运行 Claude Code；把执行放入沙箱，使长时间运行的智能体保持安全；通过 MCP 集成暴露部署能力；并在智能体真正需要回滚之前，先反复演练回滚路径。


| 传统方式                                                                     | AI 原生方式                                                                                   |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| 流水线执行确定性脚本，任何需要判断的事情都等待人来处理，例如识别偶发测试、写变更日志、判断构建为什么失败。部署和回滚依靠人在压力下照着手册操作。 | Claude 在流水线沙箱中非交互处理需要判断的步骤，只持有范围受限的凭证。部署工具通过 MCP 提供，因此编写、测试变更的工作流也能在组织为不同环境定义的关卡内完成发布和回滚。 |




#### 如何起步

- **前置条件：** Claude 已进入 PR 审查闭环，Hook 已作为审批关卡。必须先有门，再让自动化加速通过这些门。
- **基础设施：** 安装 `claude-code-action` 的 CI 平台，或任何能调用 `claude -p` 的 runner；可通过 API 使用模型，若流量必须留在组织云协议下，则用 Bedrock、Foundry 或 Vertex；面向部署目标的 MCP 服务器；没有长期生产凭证的智能体任务沙箱配置。



#### 执行步骤

1. 平台工程师先从只读判断任务开始。在流水线中用 `claude -p` 分析失败构建、总结偶发测试或起草变更日志。
2. 再把写操作放到现有关卡之后，例如修复 lint、更新生成文档，或通过 `@claude` 处理审查意见。智能体写的一切都必须经分支保护形成 PR，它不能直接推送到主分支。
3. 在沙箱中执行。智能体任务运行在受网络政策约束的容器中，只使用短期、范围受限的令牌，默认没有生产凭证。
4. 通过 MCP 暴露部署。把部署、状态和回滚变成按环境限定的工具，让部署能力成为白名单，而不是一段携带凭证的 shell 脚本。
5. 按环境划分自主程度：开发环境可以自由部署；生产环境由智能体准备发布、发布经理授权，并由 Hook 强制生产关卡；预发布环境介于二者之间。
6. 回滚应是流水线中演练最多的路径：智能体只需一条命令即可运行，并在预发布环境定期执行。阶段 6 在控制带被突破时会调用它，因此必须提前证明可靠。



#### 流水线步骤示例

```yaml
- name: Triage failed build
  if: failure()
  run: >
    claude -p "读取 out/build.log 中的构建日志。找出最可能的原因，
    判断失败是偶发问题还是真实问题，并为 PR 线程写一段三行总结。" >> triage.md
```



#### 治理注意事项

核心原则是：智能体可以行动到生产关卡为止，但不能越过关卡。以下措施保证这一点：

- 分支保护把智能体写的任何内容都转成 PR，不存在直达主分支的路径。
- 生产部署 Hook 会阻止发布，直到指定发布经理授权。每次非交互运行都使用智能体自己的身份，因此流水线日志能区分智能体做的事和触发它的工程师做的事。
- 分环境权限等级规定智能体在到达关卡前可以做多少。



#### 如何衡量

- **领先指标：** 无需通知人就完成分析的流水线失败占比，可从 CI/CD 日志统计。
- **滞后指标：** DevOps Research and Assessment（DORA）指标；CI 系统和部署工具通常已经会输出这些数据。



## 阶段 6：维护

> 闭环形成：某个触发器在无需人启动的情况下调用 Claude；Claude 的发现再以 `intent.md` 形式回到流水线中。



### 维护并闭合循环

前五个阶段都需要人来启动第一步。维护阶段则把重点转向 Claude 的自主运行，让整个循环真正闭合。

例如，持续运行的监控智能体在有人提交缺陷工单后，可以自动创建 `intent.md`，依次进入需求、计划、构建、测试和审查。阶段 6 以无界面方式运行；各阶段之间设置独立的信心关卡——可以是确定性检查，也可以是对抗式审查智能体——决定上一阶段的产物继续向前，还是升级给人处理。


| 传统方式                                                                                 | AI 原生方式                                                                                                         |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 维护是被动阶段。所有工单和事故都要等人行动并重新启动流程。凌晨 3 点的告警可能被漏掉；工单可能一直躺在积压列表；如果又出现紧急问题，复盘行动甚至可能永远进不了代码库。 | 控制带越界、工单、频道消息或定时计划等触发器，无需人在链路中即可调用 Claude。Claude 负责诊断，只能通过设有关卡的路径行动，并把发现写成 `intent.md` 进入前述阶段。人负责分诊和审查，不必再负责启动。 |




### 闭合循环

确定性脚本持续观察生产环境，在控制带被突破时调用 Claude。指标越界监控是自主闭环的典型例子；本阶段最后的 Claude Tag 则说明如何处理从沟通频道进入的工作。

#### 如何起步

- **前置条件：** 用 `intent.md` 为循环提供可重新开始的结构化输出；Claude 加速的 PR 审查；作为行动边界的 Hook；CI/CD 回滚路径（最高自主等级会调用它）。
- **基础设施：** 检测脚本可查询的指标存储，如 Prometheus、CI 系统 API 或同类系统；代码仓库只读权限；在 CI 中非交互运行 Claude Code 的方式，或用于接收 Webhook 的 Agent SDK 服务。



#### 执行步骤

1. 服务负责人或平台工程师选择一项有稳定滚动基线的指标，例如 CI 测试失败率、部署后 5xx 比例或 PR 周期时间。
2. 编写检测脚本，通常在滚动窗口上计算均值和标准差，并使用 Western Electric 等规则，让控制带既能捕获突发尖峰，也能发现缓慢漂移。脚本受版本控制并有单元测试；检测必须完全确定性，不让模型参与。
3. 在版本控制的配置中定义响应等级（见下方 `bands.yaml`）：1σ 只记日志；2σ 只读调用 Claude 诊断；3σ 允许 Claude 行动，但只能创建进入审查关卡的 PR，或触发预先批准的运行手册。
4. 触发层可以是 GitHub/GitLab 定时工作流、现有监控栈的 Webhook，或内网 Cron Job。Claude 以无状态方式运行：要么作为 CI runner 上的非交互步骤，要么作为沙箱容器中的 Agent SDK 服务。因为运行无状态且非交互，一个循环可以在无人启动的情况下自行开始和结束。
5. 智能体按照阶段 1 格式把诊断写入 `intent.md`，包含异常及证据、预期结果、受影响系统和待确认问题。此后，它像其他变更一样进入流水线。
6. 服务负责人或值班工程师处理分诊队列，把面向产品的发现交给产品负责人，并选择立即修复、排期或忽略。忽略记录可用于调整控制带、减少噪声。
7. 修复上线后，为该事故增加一项评测，避免今后再次出现同类问题。



#### 示例：监控 CI 测试失败率的 `bands.yaml`

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```



#### 治理注意事项

响应等级边界来自受版本控制的配置；权限和托管设置禁止访问生产环境。每次调用、发现和分诊决定都带时间戳记录。服务负责人负责分诊和批准；后续变更进入正常 PR 审查关卡；智能体能触发的运行手册均已预先批准。

#### 如何衡量

- **领先指标：** 从控制带越界到分诊队列中出现 `intent.md` 的时间，并与过去从事故发生到产生复盘行动的耗时比较。检测日志包含越界时间戳和事故等级。
- **滞后指标：** 最终变成已合并修复的发现占比（比较分诊队列和真实 PR 历史）；同类事故的复发次数应随修复和评测积累而下降。



#### 示例场景

- CI 测试失败率超过 3σ 时，智能体隔离偶发测试或创建回滚 PR，是否通过由审查关卡决定。
- 部署后 5xx 比例超过 3σ，且时间窗口内发生过部署时，智能体触发现有回滚流水线。
- PR 周期时间触发漂移规则时，智能体为工程管理层生成报告。这说明同一套执行框架既能监控生产指标，也能监控流程指标。

> 检测始终是确定性的。只有控制带被突破后才调用 Claude；响应等级决定它能做什么。



### 定期扫描代码库

一次安全扫描，只能说明某个模型在某个时间点看到的代码库状态，而这两方面都会过时：代码每周都在变化，每代新模型也可能发现上一代遗漏的漏洞。AI 原生做法是按计划自动扫描，不让人处于启动链路中；扫描发现则像其他代码变更一样经过相同关卡。

Claude Security 是托管式定期扫描方案。连接 GitHub 仓库后，扫描会在 Anthropic 基础设施中使用 Claude Mythos 5 运行；每项发现先验证再报告，并附置信度评级。建议补丁可在网页版 Claude Code 中审查和应用。组织无需直接访问模型本身，也能获得扫描结果。


| 传统方式                                                              | AI 原生方式                                                                                              |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 安全扫描是发布或审计前才启动的一次事件。报告进入跟踪器，由人慢慢清理积压，直到下一次扫描；两次扫描之间的代码只能依赖 PR 审查。 | 对每个已连接仓库按计划使用当前能力最强的模型扫描，发现经过验证后才交给人。单个 PR 能解决的问题进入审查关卡，更大问题写成 `intent.md`。覆盖状态以最近一次扫描日期为准，而不是第一次扫描。 |




#### 如何起步

- **前置条件：** 阶段 5 的 PR 审查关卡和审批 Hook，使扫描发现与其他变更一样接受审查；对于无法由单个 PR 解决的问题，使用阶段 1 的 `intent.md` 格式。
- **基础设施：** Claude Security 目前以公开测试形式提供给 Claude Enterprise 组织。目标必须是云托管的 `github.com` 仓库，并安装 Anthropic GitHub App；启用网页版 Claude Code；开启 Extra Usage 并设置消费上限；运行扫描的人员需要 premium seat；管理员还需在 `claude.ai/admin-settings/claude-code` 启用功能。扫描按 Mythos 5 消耗计费，因此支出上限应与仓库规模和数量匹配。



#### 执行步骤

1. 安全负责人连接仓库，并按仓库、服务或团队组织成项目，从一开始就明确发现的所有权。
2. 对最关键仓库运行首次完整扫描，包括过去已被其他工具或旧模型扫描过的仓库。把它作为基线，并预计会在原本认为干净的代码中发现问题。
3. 为每个项目设置计划。活跃服务可默认每周扫描；大型或混合型仓库可限定目录或分支。
4. 结合置信度分诊发现。忽略时必须填写原因，这样决定会被记录，同一发现也不会在下次运行时重新当作新问题。
5. 对边界清晰的问题，在网页版 Claude Code 中打开建议补丁，审查后像其他变更一样送入 PR 关卡。提出修复的智能体无权批准它。
6. 对超出单个补丁范围的问题，例如架构弱点或跨服务重复模式，按阶段 1 格式写成 `intent.md`，从规划阶段开始。
7. 修复进入生产后，为该类漏洞增加一项持续评测，使引导智能体的配置此后始终接受该类测试。
8. 用 CSV、Markdown 或 Webhook 导出发现，让现有跟踪器和审计系统继续作为审计人员熟悉的事实来源。



#### 治理注意事项

扫描在组织的管理员控制下运行：连接哪些仓库、谁拥有扫描席位、支出上限多少都集中设置。每项发现都有验证结果和置信度，每次忽略都有原因，因此扫描历史完整记录“发现了什么、修复了什么、哪些风险被有意识接受”。

修复必须经 PR 审查关卡和分支保护进入生产，扫描本身不能直接上线代码。Claude Security 是对现有静态分析和依赖扫描的补充：确定性检查继续留在 CI；模型驱动扫描负责寻找那些依赖上下文、传统检查不擅长发现的漏洞。

#### 如何衡量

- **领先指标：** 已连接仓库中设置了扫描计划的比例；从报告发现到补丁进入 PR 审查关卡的时间，可从扫描历史和 PR 元数据读取。
- **滞后指标：** 定期扫描发现的漏洞与生产环境或外部报告才发现的漏洞之比；多次扫描后每次发现数的趋势应随修复和评测积累而下降。



### 用 Claude Tag 参与值班响应

事故也可能从 Slack、Teams 等工作沟通应用进入。例如晚上 10 点，事故频道中出现一条要求紧急修复的 Slack 消息，现在可以立即处理。Claude Tag（目前在 Slack 中公开测试）让 Claude 以自己的身份成为频道成员。这样，每起新事故都有第一响应者，响应过程也会进入闭环，并成为未来事故的记忆。

对话和组织知识都留在频道中，频道内任何人都可以引导并执行响应。团队成员可实时验证假设、探索新方案和调查问题，频道历史增强了可审计性。Claude 通过 MCP 确认指标已恢复到基线，在对话线程中报告，再把复盘写入受版本控制的经验文件，供未来调查读取。

Claude Tag 不只处理事故。它可通过 MCP 在工单中被标记，也可接受频道请求，并用同一方式分诊。小而明确的修复会形成 PR 并经过审查关卡；更大的问题写成阶段 1 的 `intent.md`，此时闭环开始自我驱动。另见 [Anthropic 如何让 Claude Tag 为 CI/CD 值班](https://claude.com/blog/ai-ci-cd-on-call)。

*频道就是审计轨迹：请求、诊断、人工授权和修复都留在处理事故的原位置。*
