## Problem

HydroZagent 的 Agent Harness 会持续执行模型产生的工具调用，但目前没有跨回合的收敛与止损机制，无法在以下情况中主动中断无效循环：

- 同一工具以相同参数和相同结果被重复调用。
- 工具错误持续累积，但模型没有改变策略。
- 任务已经得到足够验证，模型仍继续扩展无关子目标。
- 单个任务的运行时间、工具错误数或 Token 消耗超过合理边界。
- 工具返回空结果、路径不存在或命令失败时，Harness 只将原始文本再次交给模型，没有将它们转换为可用于决策的结构化信号。

2026-08-28 的真实会话中，一个 diff 内容传递问题持续了 40 分 26 秒，产生 108 次工具调用和 27 次工具错误。其中同一条失败搜索连续执行 23 次；在 LSP 检查已通过后，又产生 44 次工具调用和 23 次错误。最终需要用户人工中断并切换模型。

这不仅是某个模型的行为缺陷。任意模型都可能进入局部循环，Harness 必须独立于模型提供确定性的资源边界和退出机制。

## Proposed outcome

HydroZagent 能够在 Agent 运行期间识别“重复失败”、“错误超支”、“资源超支”和“无进展”，并在造成大量时间或 Token 浪费之前，以可解释、可恢复的方式暂停当前运行。

当保护机制触发时，系统应：

1. 在下一次重复工具调用或模型请求发生前停止无效执行。
2. 记录结构化的触发原因、当前计数、最近证据和未完成目标。
3. 明确告知用户为何暂停，而不是显示笼统的“执行失败”。
4. 保留完整会话和任务状态，允许用户选择重新规划、调整限额、切换模型、继续或终止。
5. 产生可供持续 eval 和后续事故复盘使用的审计记录。

## Affected users and systems

- 使用 TUI、RPC、PiDeck 桌面端或其它 pi 客户端运行编码任务的用户。
- `packages/agent` 中的 Agent 循环、工具执行前后钩子与使用量记录。
- `packages/coding-agent` 中的会话编排、自动重试、上下文压缩、会话事件与配置。
- PiDeck 对暂停原因、资源使用和恢复操作的展示。
- 模型或 Agent 配置的持续 eval 和发布门禁。

## Constraints

- 遵守现有边界：pi 负责 Agent 行为与工具调度；PiDeck 只负责展示和用户操作，不在 UI 层复制第二套 Agent 循环。
- 保护机制必须由 Harness 确定性执行，不能只依赖系统提示词或某个模型自律。
- 保持现有 `beforeToolCall` / `afterToolCall`、自动重试、上下文压缩和用户中断语义。
- 不得将有意义的重复执行一律视为循环，例如测试重跑、轮询、分页读取和用户明确要求的重试。
- Token 预算需要兼容不同 provider 的用量字段、缓存计费方式和用量数据缺失；缺失数据不得使其它预算失效。
- 并行工具调用、steering message、follow-up queue 和模型切换后的计数必须确定且可重放。
- 暂停和恢复不得丢失已完成的工具结果，也不得留下永远处于 running 状态的工具调用。
- 新增配置和会话事件必须兼容现有会话数据和 RPC 客户端。
- 初次上线需要可观测、可关闭、可回滚，避免误判阻断正常长任务。

## Out of scope

- 本阶段不确定调用次数、错误数、时间和 Token 的具体默认阈值。
- 本阶段不选定重复调用指纹或“无进展”判定的具体算法。
- 不通过更换默认模型、针对 Qwen 写特判或单纯增加提示词解决问题。
- 不在本改动中修复原会话里的 diff UI 问题。
- 不在 intent 阶段确定 PiDeck 的最终视觉与交互设计。

## Success measures

- 时间、Token、工具错误和无进展中任一预算超限时，会话产生可机读的结构化事件，事件包含原因、已用量、限额、触发位置和恢复选项。
- Harness 暂停后不再发起新的 provider 请求或工具调用，直到用户或受信的上层编排者明确处理。
- 用户可在不丢失原任务上下文的情况下重新规划、放行一次、调整限额或终止任务。
- 对现有正常工具链、有界重试、并行调用、长时间命令、上下文压缩和用户中断的回归测试通过。
- 持续 eval 能够在更换模型、修改 Agent 提示、Harness 配置或工具定义时自动重放本次事故类型。
- 可以持续观测重复调用率、误报率、预算触发率、用户人工中断率、每任务工具调用数和非缓存 Token 消耗。

## Open questions

1. 哪些保护应分为提醒、强制重新规划和硬暂停三个级别？
2. 默认预算应按单次用户任务、单次 Agent run、整个 session，还是同时按多个维度累计？
3. 何种证据可以重置“无进展”计数：新文件、新搜索命中、代码 diff、测试状态变化，还是模型提供的显式重新规划？
4. 如何区分正常轮询、用户要求的重试与无意义的重复调用？
5. 用户手动放行后，是仅允许一次越过，还是在本次任务中暂时提高限额？
6. Token 限额应使用总 input、非缓存 input、计费 Token、成本估算，还是组合指标？
7. 子 Agent、并行任务和模型 fallback 应共享父任务预算，还是获得独立子预算？
8. 哪些预算可由用户配置，哪些是防止产品失控而不允许完全关闭的安全上限？
